# Архитектурное правило: Умная модульность (Feature-as-a-Module)

1. НОВЫЕ СИСТЕМЫ И МЕХАНИКИ:
   - Если задача представляет собой самостоятельную игровую подсистему, механику или экран (более 30–40 строк логики):
     ЗАПРЕЩЕНО писать её реализацию внутри `res://main.gd`.
   - Создавай изолированный модуль в соответствующей подпапке `res://scripts/`:
     * `ui/` — для меню, окон, HUD и оверлеев.
     * `managers/` — для систем расчётов, таймеров, логики правил, событий и состояния.
     * `resources/` — для структур данных (Resource).
     * `audio/` — для звуковых эффектов.
   - Оформляй модуль через `class_name`, наследуйся от минимально необходимого класса (`Node`, `Control`, `RefCounted`).
   - Для связи с игрой используй слабое зацепление через сигналы (`signal`), избегая прямых циклических зависимостей от `main.gd`.
   - В `res://main.gd` добавляй ТОЛЬКО подключение: инициализацию экземпляра и подписку на сигналы (в пределах 5–15 строк).

2. ИСКЛЮЧЕНИЯ (КОГДА НОВЫЙ ФАЙЛ СОЗДАВАТЬ НЕЛЬЗЯ):
   - Мелкие багфиксы, опечатки, настройка констант и параметров — правь строго точечно по месту.
   - Микро-механики до 25 строк (например, разовый `Tween` анимации камеры, смена цвета шейдера, добавление одной клавиши управления) — реализуй прямо в целевом скрипте без пложения лишних микро-файлов.

3. ПРАВИЛА ЧИСТОТЫ GODOT 4:
   - При удалении динамических объектов всегда вызывай `queue_free()`.
   - Перед обращением к метаданным узлов всегда проверяй их наличие: `if node.has_meta("key"): ...`.
   - Не создавай пустые файлы без реальной кодовой базы.
